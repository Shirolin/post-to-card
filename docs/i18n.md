# 语言（i18n）

界面、卡片、弹窗、注入按钮的语言从一处派生：`src/content/locales/` 下每语言一个字典文件，
`src/content/i18n.ts` 组装成 `TRANSLATIONS: Record<Locale, Translations>` 并管解析。
Chrome 的 `public/_locales/` 是第二份目录（manifest 读不了 TypeScript），`localeDirName` 是两者
之间唯一的映射。

## 为什么是类型化字典，不是 `t('key')`

`Translations` 是接口，每个字典标着它，所以漏键、拼错键、多键都是 `tsc` 的编译错误，而不是运行时
回退到英文。调用点写 `t.copyImage`，改名靠编辑器重命名而不是全文搜索。参照项目用的 `t('copyImage')`
把这一切推迟到运行时，本项目没有理由退回去。

接口在 `src/content/locales/types.ts` 而不是 `i18n.ts`：字典要 import 它，`i18n.ts` 要 import 字典，
放一起就成环。

## 不引 ICU 复数

唯一真正区分单复数的地方已经由 `previewSummary` / `previewSummarySingular` 成对解决，选择函数在
`formatPreviewSummary`。其余带计数的键写成中性句式。ICU MessageFormat 要多一个依赖，还要 14 门翻译
各写一套语法，只换来一条文案的改进。

代价是已知的：`replies` / `reposts` / `likes` / `views` / `bookmarks` 是裸名词，单条回复会读作
`1 Replies`。它们只出现在 `title` / 悬停文本里，不在画面像素上。

## 占位符

`{name}` 由 `String.prototype.replace` 单次替换，所以一个模板里同名占位符只换第一处。逐键的占位符
集合必须与 en-US 完全相等，由 `i18n.10` 守——它比较排序后的多重集，因此重复的 `{count}` 也算违规。

## 加一门语言

1. `src/content/locales/<id>.ts`：`export const <name>: Translations = {…}`，照 `en-US.ts` 抄键。
2. `src/content/locales/types.ts` 不动（键表是共用的）。
3. `src/types/card.ts` 的 `Locale` 联合加 id。
4. `src/content/i18n.ts`：`SUPPORTED_LOCALES`、`TRANSLATIONS`、`LOCALE_ENDONYMS` 三处各加一项；
   若这门语言有地区变体（`zh-Hant`、`pt-PT` 那样）再补 `TAG_ALIASES`。
5. `src/content/popupCopy.ts` 加一块。
6. `public/_locales/<Chrome 目录名>/messages.json`，键照 `en_US` 抄。
7. `tests/tiers/tier_hygiene.test.ts` 的 `CHROME_LOCALE_DIRS` 允许表加目录名。
8. 在 harness 里过一眼长词是否溢出（见 AGENTS.md 的「预览」）。

键齐平、占位符、目录名、endonym 齐全、`dist/` 是否真的带上了 `_locales`，都由门禁算，不用在文档里
再抄一份。

## `_locales` 的两个坑

**目录名必须是 Chrome 表里的下划线形式**，而且只在有地区码时带地区：`en_US`、`zh_CN`、`zh_TW`、
`pt_BR`，但 `de`、`fr`、`ja`、`ko` 是裸的。写成 `de_DE`、`pt_PT` 或连字符的 `zh-CN` **不会报错**——
Chrome 静默回落到 `default_locale`，表现是「翻译做了却没生效」。`hygiene.10` 的允许表是唯一防线。

**`public/` 只被 `background` 和 `content` 两次 build 复制**（`popup` / `hook` 传 `publicDir: false`），
所以 `dist/_locales` 的存在依赖那两次 build 之一。`T5.3.9` 检查产物里真有这棵树。

## Auto

`DEFAULT_CARD_CONFIG.locale` 是 `'auto'`，意思是跟随 `navigator.language`。存储里存的是**偏好**而不是
解析结果：`sanitizeLocalePref` 保留 `'auto'`，`resolveLocale` 才把它解析成具体语言。把两步合成一步
会把「跟随浏览器」在第一次保存时变成一门钉死的语言。

两者对「有语言标签但本 build 没有」的回答**不同**，这是刻意的：

| 输入 | `sanitizeLocalePref`（存储） | `resolveLocale`（渲染） |
|---|---|---|
| `'auto'` / 空 / 垃圾 | `'auto'` | 跟随浏览器 |
| `'ja'`、`'fr-CA'`、`'pt_PT'` | 归一到具体 id | 该语言 |
| `'nl-NL'`、`'sr-Latn-RS'` | `'auto'` | `en-US` |

存储里记不下「荷兰语」这个它没有的选择，所以退回 Auto；渲染时用户明确点了名，最诚实的读法是默认
语言，而不是这台机器碰巧说的语言。

标签解析按**最长前缀**而不是按第一个 `-` 切开：`zh-Hant-HK` 要经 `zh-Hant` 到 `zh-TW`，切开会落到
`zh` 印出简体。

弹窗的 `SUPPORTED_LOCALES.includes(prefs.locale)` 有意不认 `'auto'`：它已经按浏览器画过首帧了，
落空正好留在原地。

## 时间戳

`zh-CN` 与 `en-US` 是手写格式，产品定过、`i18n.4/.5` 钉着字节；其余语言走
`Intl.DateTimeFormat(locale, { dateStyle: 'medium', timeStyle: 'short' })`。改这两条手写分支前先想清楚：
`Intl` 的同一格式在不同平台会不一样。
